# Corrections

This file covers the corrections made for the AAAI-27 #44087 rebuttal campaign (`protocol_version: automode_rebuttal_corrected_v1`). It is split into four parts:

* **A. Bugs**: code that did not do what it claimed.
* **B. Protocol changes**: deliberate choices that change what is measured.
* **C. Unverified provenance**: what we cannot establish about earlier results.
* **D. Open risks**.

Corrected-protocol numbers are **not comparable** with numbers from earlier code, and the two must never be pooled. The campaign writes to fresh output roots, and earlier outputs can never satisfy its completion check: the run id and job identity changed, and COMPLETE must match the identity.

## B. Protocol changes (corrected protocol choices)

1. **Score statistic** (`score_collection: optimizer_step`): the completed accumulation-window gradient, after tail rescaling and before clipping, sampled once per update. The score is the root of the mean squared component, averaged across the switching window. This changes the statistic relative to the submission (A10). It does **not** make the score comparable across adapter and base modes, nor invariant to the LoRA gauge (A → cA, B → B/c changes it while BA is unchanged; `test_rms_score_is_not_invariant_to_lora_gauge_rescaling`). The lower-tail percentile rule is unchanged: `score >= percentile(scores, t)` → base mode.
2. **Training targets**: same prompt template text, but prompt and target are tokenized separately, `" " + target`, with **EOS appended** (the submitted pipeline appended none, so models never learned to stop). Over-long prompts are left-truncated keeping BOS.
3. **GSM8K scoring**:
   * extraction `gsm8k_first_hash_then_last_number_v2`: the first `####`, else the last number;
   * Decimal normalisation;
   * every one of the k=3 samples votes, with invalid samples counted as one "invalid" option; plurality, with ties going to the first-seen option; an invalid win is incorrect;
   * metric `gsm8k_maj3` over all 1,319 test items;
   * full records are stored.
4. **Optimizer state across switches**: Adam moments are kept for parameters that stay trainable (A3), as the supplement describes. The submitted code reset all moments at every switch, which changes AutoMode's training dynamics.
5. **No terminal switch**; the last allocation recorded is the one that trained the final update.
6. **Seeding**: data order from `data_seed`; generation from `evaluation_seed` (20261029) per batch; adapter resets and the `fixed_mixed` allocation from dedicated generators. GPU kernels are **not** forced deterministic, so equal seeds need not give bitwise-equal GPU runs (the settings are recorded in `environment.json`).
7. **LR schedule**: the manifest uses **linear** warmup/decay. The legacy grid never set `lr_scheduler`, so legacy runs used `RunConfig`'s default, **cosine**. The kit describes linear as the paper's schedule; we have not verified this.
8. **Attention**: `eager` for Gemma-2 (attention-logit soft-capping).
9. **Retention evals**: a 2048-token context budget, deliberate shot reduction, a fixed subset. Not comparable with earlier MMLU/ARC numbers.

## C. Unverified historical provenance

* Which code and notebook version produced each number in the submission is not established here. `core.py` refers to earlier 2B/9B notebooks with known prefix-matching and sawtooth-LR bugs. `AutoMode_GLUE.ipynb`, `AutoMode_GSM8K.ipynb` and the final report PDF were not available to this audit.
* The saved outputs of `notebooks/driver_gpu2_5070.ipynb` show legacy Gemma-2-2B runs (full_ft, LoRA, AutoMode, topk_block, LISA, AdaGradSelect, …) executed through this package. No LR traces were saved in the notebooks. The zero-LR effect on LISA/AdaGradSelect (A2) is therefore inferred from the code path and reproduced in a unit test, but was **not observed** in those runs.
* Whether submitted runs hit the prompt-mask leak (A9) depends on prompt lengths per track (likelier for MetaMath/Alpaca than GSM8K); it is not quantified.
* Run-id collisions (A7) could have let one configuration be skipped as "complete" because of another. In the saved outputs, the smoke test used a separate output root and a different epoch count, so no collision is *demonstrated*.
* All submitted base-mode training (AutoMode promoted layers, full-FT, top-k blocks) used pure-bf16 AdamW updates (see D1).

## D. Open risks / unresolved

1. **bf16 base updates largely round away.** The submitted protocol and the supplied manifest keep q/v base weights and their Adam state in bf16. Adam's update magnitude is ≈ LR (2e-5, decaying), while bf16 spacing near |w| = 2⁻⁶…2⁻⁵ is ≈ 1.2e-4, so round-to-nearest discards most updates.

   Synthetic check (executed; `TEST_REPORT.md`): for w ~ N(0, σ), the fraction of elements changed by one ±lr step was 0.30 (σ = 0.02, lr = 2e-5) and 0.21 (σ = 0.03). At lr = 1e-5 it was 0.155 and 0.104.

   The real fraction for Gemma-2-9B is measured per update (`base_update_changed_fraction_mean`, `logs/base_update_probe.json`) and shown in the pilot report. `base_weight_dtype: "float32"` (fp32 q/v master weights plus bf16 autocast) is implemented and CPU-tested but **off** in the manifest. Turning it on is a protocol change that changes every identity. **Decide after reading the pilot.**
2. **No GPU test was executed locally** (the development machine has no NVIDIA GPU). Remote preflight runs the whole suite with `AUTOMODE_TEST_DEVICE=cuda`, and fails, rather than skips, without CUDA. It also checks a real bf16 kernel launch and records whether the device's arch is in the torch build. Blackwell (sm_120) compatibility of the rental image is **not verified** here.
3. **Training-mode dropout** differs between modes (it applies only to the adapter path), even though the eval-mode function is preserved across promote/demote.
4. **Budgets differ by design**: `static_qv` > `fixed_mixed` ≈ AutoMode's post-selection instantaneous budget. AutoMode's time-integrated budget depends on its schedule (reported as the update-weighted trainable count).
5. **ETA** is pilot-based (post-promotion step time × steps + scaled generation time + export, × 1.25). It is approximate, not a guarantee.
6. **Revision resolution** happens per worker at preflight. If HF `main` moves between workers' preflights, the notebook's equality gate fails; re-run with revisions pinned in the manifest.
7. **Interrupted runs restart from scratch**; there is no mid-training resume.
